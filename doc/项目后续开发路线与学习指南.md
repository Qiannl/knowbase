# 知集项目后续开发路线与学习指南

## 1. 文档目的

这份文档用于指导“知集”个人知识库项目从当前状态逐步完成第一个可用版本。

项目的主要目的不只是完成页面，还包括学习以下能力：

- Next.js App Router 的路由、布局和服务端组件
- Auth.js 的登录、Session 与权限控制
- Prisma 与 PostgreSQL 的数据建模和查询
- React Hook Form 与 Zod 的表单处理
- TanStack Query 的客户端服务器状态管理
- 从静态原型拆分出可维护的 React 组件
- 用工程化方式处理错误、安全、测试与部署

`doc/知集·个人知识库（手账杂志风）.html` 是初步页面原型，主要用于表达视觉风格和产品方向，不是最终实现必须逐像素照搬的契约。实现过程中可以根据组件复用、响应式布局、无障碍、数据结构和权限逻辑调整设计。

# 阶段一：完成登录闭环

## 4. 阶段目标

用户可以在 `/login` 输入用户名和密码。服务端验证成功后写入 Session Cookie，并跳转到首页；验证失败时显示安全、明确的错误信息。

## 5. 需要学习的知识点

### 5.1 身份认证、Session 与权限的区别

- 身份认证：确认用户是谁，例如校验用户名和密码。
- Session 管理：登录成功后，让后续请求持续识别该用户。
- 权限控制：确认该用户能做什么，例如只有管理员可以创建用户。

三者的关系是：

```text
登录表单
  → Credentials authorize
  → 验证数据库用户和密码
  → JWT Cookie
  → Session
  → 页面和服务端操作进行权限判断
```

### 5.2 Server Action 的职责

登录 Server Action 应负责：

1. 接收表单数据。
2. 使用 Zod 做运行时校验。
3. 调用 Auth.js 的 `signIn("credentials")`。
4. 将可预期的登录失败转换为表单可显示的结果。
5. 登录成功后跳转。

它不应该自己重复查询用户和比较密码，因为这些职责已经属于 Credentials 的 `authorize()`。

### 5.3 为什么登录失败不能暴露过多信息

无论是用户名不存在还是密码错误，页面统一提示“用户名或密码错误”。这样可以避免攻击者通过错误信息枚举有效账号。

## 6. 建议目录

```text
src/
├── actions/
│   └── auth.action.ts
├── app/
│   └── (auth)/
│       └── login/
│           └── page.tsx
├── components/
│   └── auth/
│       └── login-form.tsx
└── lib/
    └── schema/
        └── auth.schema.ts
```

页面和表单建议拆开：

- `page.tsx` 默认保持 Server Component，负责页面外壳和服务端逻辑。
- `login-form.tsx` 是 Client Component，负责输入、提交状态和错误展示。
- `auth.action.ts` 是服务端边界，负责安全地调用 Auth.js。

## 7. 实施顺序

### 7.1 指定自定义登录页

在 Auth.js 配置中加入：

```ts
pages: {
  signIn: "/login",
},
```

作用是让 Auth.js 知道项目自己的登录页在哪里，避免认证失败时进入 Auth.js 默认页面。

### 7.2 设计统一的 Action 返回结构

建议业务失败使用可判别联合类型，而不是同时混用 `Response`、普通对象和异常：

```ts
type ActionResult<T = undefined> =
  | { success: true; data: T }
  | {
      success: false;
      message: string;
      fieldErrors?: Record<string, string[]>;
    };
```

可预期的表单错误返回 `success: false`；数据库断开等不可预期错误再交给异常处理和日志。

### 7.3 创建登录 Server Action

登录 Action 应明确处理：

- Zod 校验失败
- Credentials 登录失败
- Auth.js 其他认证错误
- Next.js 重定向异常不能被错误捕获后吞掉

不要在 Action 中记录明文密码，也不要把原始异常堆栈返回浏览器。

### 7.4 创建登录表单

登录表单使用：

- React Hook Form 管理表单状态
- `zodResolver` 复用登录 Schema
- Server Action 完成最终服务端校验

客户端校验提升体验，服务端校验保证安全。即使客户端已经校验，服务端仍必须再次校验，因为客户端请求可以被绕过或伪造。

### 7.5 完成登录后的服务端验证

暂时在首页调用：

```ts
const session = await auth();
```

验证以下字段运行时真实存在：

- `session.user.id`
- `session.user.username`
- `session.user.role`

这里验证的是完整数据链：

```text
数据库 User
  → authorize 返回 User
  → jwt 回调保存字段
  → session 回调组装 Session
  → auth() 读取 Session
```

## 8. 阶段验收标准

- `/login` 可以正常访问。
- 空用户名、短密码有字段级提示。
- 错误账号显示统一错误信息。
- 正确管理员账号可以登录。
- 登录成功跳转首页。
- 已登录用户访问 `/login` 会跳回首页。
- 未登录用户访问受保护页面会跳到 `/login`。
- Session 中能读到真实的 `id`、`username`、`role`。
- 浏览器和服务端日志中没有明文密码。

# 阶段二：路由分组与 Dashboard Layout

## 9. 阶段目标

建立登录页与登录后应用区域的清晰边界，让文档、AI、设置和管理页面共享侧边栏与顶部区域。

## 10. 推荐路由结构

```text
src/app/
├── layout.tsx
├── (auth)/
│   └── login/
│       └── page.tsx
└── (dashboard)/
    ├── layout.tsx
    ├── page.tsx
    ├── docs/
    │   ├── page.tsx
    │   ├── new/page.tsx
    │   └── [id]/
    │       ├── page.tsx
    │       └── edit/page.tsx
    ├── ai/page.tsx
    ├── settings/page.tsx
    └── admin/
        └── users/page.tsx
```

`(auth)`、`(dashboard)` 是路由组，不会出现在 URL 中。

例如：

```text
app/(auth)/login/page.tsx       → /login
app/(dashboard)/docs/page.tsx   → /docs
```

## 11. Layout 的分层职责

### 11.1 Root Layout

根布局只放全站基础设施：

- `<html lang="zh-CN">`
- `<body>`
- 全局 CSS
- 字体
- Metadata
- 真正全站需要的 Provider

不要因为某个局部页面需要交互，就把整个根布局改成 Client Component。

### 11.2 Dashboard Layout

Dashboard Layout 负责：

- 服务端调用 `auth()` 获取当前用户
- 未登录时重定向
- 侧边栏
- 顶部栏
- Dashboard 范围的 Provider
- 将 Session 的必要信息传递给用户菜单

Layout 是共享 UI。页面切换时，Layout 可以保留状态并避免重复挂载。

## 12. 原型拆分思路

不要把原型 HTML 整体复制到一个 React 文件中。建议拆分为：

```text
components/
├── layout/
│   ├── sidebar.tsx
│   ├── topbar.tsx
│   └── dashboard-shell.tsx
├── common/
│   ├── page-header.tsx
│   ├── empty-state.tsx
│   └── confirm-dialog.tsx
└── docs/
    ├── doc-card.tsx
    └── doc-list.tsx
```

拆分标准不是“文件越小越好”，而是组件是否拥有明确、稳定、可复用的职责。

## 13. 阶段验收标准

- 登录页不显示 Dashboard 侧边栏。
- 登录后的页面共享同一套侧边栏。
- 页面切换使用 Next.js `Link`，不再使用原型中的 DOM 手动切换。
- 未登录不能访问 Dashboard。
- 当前用户信息来自服务端 Session。
- 管理员菜单只对管理员展示，但服务端仍有独立权限检查。

# 阶段三：按需配置 SessionProvider

## 14. 什么时候需要 SessionProvider

Server Component 使用：

```ts
const session = await auth();
```

不需要 SessionProvider。

Client Component 使用：

```ts
const { data: session } = useSession();
```

才需要 SessionProvider。

适合使用 `useSession()` 的场景：

- 客户端用户菜单
- 客户端退出登录按钮
- 更新个人资料后刷新 Session
- 客户端根据 Session 更新局部 UI

## 15. Provider 作用域原则

Provider 应放在所有使用者的最近共同父级，而不是默认放在根布局。

本项目优先考虑放在 `(dashboard)` 范围，因为登录页通常不需要 `useSession()`。

建议创建：

```text
src/components/providers/session-provider.tsx
```

这个文件需要使用：

```ts
"use client";
```

Dashboard Layout 本身仍可保持 Server Component，并把 `children` 传给客户端 Provider。通过 `children` 组合不会自动把所有服务端页面变成 Client Component。

## 16. 安全原则

SessionProvider 只解决客户端读取 Session 的便利性，不是安全边界。

下面的代码只能控制显示：

```tsx
{session.user.role === "admin" && <AdminMenu />}
```

真正的权限仍需在服务端检查：

```ts
const session = await auth();

if (session?.user.role !== "admin") {
  // 拒绝操作
}
```

## 17. 阶段验收标准

- SessionProvider 只覆盖确实需要客户端 Session 的区域。
- 根布局没有因为 Provider 被整体改成 Client Component。
- 用户菜单可以显示当前用户名和角色。
- 退出登录后页面正确跳回 `/login`。
- 服务端 Action 不依赖前端传入的角色。

# 阶段四：先实现服务端文档列表

## 18. 阶段目标

登录用户可以看到自己的文档列表。先使用 Server Component 和 Prisma 完成最小版本，不急着引入 TanStack Query。

## 19. 数据所有权

`Document` 通过 `userId` 属于某个用户：

```text
User 1 ─── N Document
```

普通用户查询文档时必须附带：

```ts
where: {
  userId: session.user.id,
}
```

不能先查询所有文档再在前端过滤。前端过滤既浪费数据，也会泄露其他用户的内容。

## 20. 推荐数据访问层

随着查询增加，建议将 Prisma 查询从页面中抽离：

```text
src/data/
└── documents.ts
```

数据访问函数负责：

- 构造明确的 Prisma 查询
- 只选择页面需要的字段
- 按用户 ID 限制数据范围
- 统一排序规则

页面负责：

- 获取 Session
- 调用数据函数
- 组合 UI
- 处理空状态

## 21. Server Component 为什么适合首屏列表

- 可以直接访问数据库，不暴露数据库凭据。
- 浏览器收到页面时已经包含内容。
- 减少客户端 JavaScript。
- 权限过滤发生在服务端。
- 暂时不需要额外 API Route。

## 22. 阶段验收标准

- 未登录不能查询文档。
- 普通用户只能看到自己的文档。
- 查询不会把正文等不必要的大字段全部返回给列表。
- 文档按明确规则排序，例如 `updatedAt desc`。
- 没有文档时显示空状态和“新建文档”入口。
- 文档卡片显示标题、摘要、标签和更新时间。

# 阶段五：文档 CRUD

## 23. 阶段目标

完成文档的新建、详情、编辑和删除，形成第一个完整业务闭环。

## 24. 推荐实施顺序

### 24.1 新建文档

学习内容：

- Zod 文档 Schema
- React Hook Form
- Server Action 写入数据库
- `userId` 必须来自 Session，不能相信前端传入
- 创建成功后的重定向或缓存刷新

### 24.2 文档详情

学习内容：

- 动态路由 `[id]`
- Next.js 16 中异步 `params`
- 根据 `id + userId` 查询资源
- 找不到或无权访问时返回 `notFound()`，避免泄露资源存在性

### 24.3 编辑文档

学习内容：

- 读取已有数据作为表单默认值
- 更新前再次检查所有权
- 使用 `updatedAt` 表示最近修改时间
- 防止用户修改不属于自己的文档

### 24.4 删除文档

学习内容：

- 破坏性操作确认
- 服务端所有权检查
- 删除成功后的导航与缓存失效
- 不根据前端隐藏按钮判断权限

## 25. 每个写操作的标准链路

```text
接收输入
  → 身份认证
  → Zod 参数校验
  → 角色或资源所有权校验
  → Prisma 写入
  → 刷新缓存或跳转
  → 返回结构化结果
```

身份和 `userId` 必须来自服务端 Session。客户端只能传递业务输入，例如标题、摘要、内容和标签。

## 26. 富文本编辑器策略

第一版不要立即引入复杂编辑器。可以先用 `textarea` 完成 CRUD 数据链，再升级到 Tiptap 等富文本编辑器。

这样可以把问题拆开：

1. 先证明数据可以正确保存和读取。
2. 再解决富文本格式、工具栏、HTML 安全和编辑器状态。

如果保存 HTML，需要额外考虑 XSS 清理，不能直接信任用户提交的 HTML。

## 27. 阶段验收标准

- 用户可以创建文档。
- 用户可以查看自己的文档详情。
- 用户可以编辑自己的文档。
- 用户删除文档前有确认提示。
- 用户无法通过修改 URL 访问或修改他人文档。
- 所有 Action 都有服务端认证、校验和所有权判断。
- 表单可以显示字段错误和业务错误。

# 阶段六：引入 TanStack Query

## 28. 为什么到这时才引入

TanStack Query 管理客户端的服务器状态，适合：

- 搜索和标签筛选
- 分页或无限加载
- 删除后局部刷新列表
- 新建、编辑后的缓存同步
- 多个客户端组件共享同一份远程数据
- 乐观更新

如果首屏只需要服务端读取一次数据，Server Component 已经足够。只有交互需求明确后，TanStack Query 的价值才清晰。

## 29. 关键概念

### 29.1 Query Key

Query Key 是缓存地址，例如：

```ts
["documents"]
["documents", { search, tag }]
["document", documentId]
```

参数会影响结果时，参数也应进入 Query Key。

### 29.2 staleTime

`staleTime` 表示数据在多长时间内被认为仍然新鲜。它不是缓存永久时间，也不是数据库数据的有效期。

### 29.3 Mutation

新增、编辑、删除属于 Mutation。成功后可使用：

```ts
queryClient.invalidateQueries({ queryKey: ["documents"] });
```

通知列表数据已经过期，需要重新获取。

## 30. Provider 配置原则

安装：

```bash
npm install @tanstack/react-query
npm install --save-dev @tanstack/react-query-devtools
```

创建：

```text
src/components/providers/query-provider.tsx
```

`QueryClient` 必须保持稳定，不能每次渲染都创建新实例，否则缓存会丢失。

Provider 可以和 SessionProvider 组合为 Dashboard Providers，但仍应保持根 Layout 为 Server Component。

## 31. 数据接口选择

TanStack Query 的 `queryFn` 需要可从浏览器调用的数据入口，通常是 Route Handler，例如：

```text
GET    /api/documents
POST   /api/documents
PATCH  /api/documents/:id
DELETE /api/documents/:id
```

如果项目已经确认使用 Server Actions 完成某些 Mutation，则按已确定的调用方式实现，不同时维护两套无必要的写入接口。

接口请求参数、响应字段和错误结构一旦确认，就严格按契约实现，不添加猜测性的字段兼容和静默回退。

## 32. 阶段验收标准

- QueryClient 在浏览器会话中保持稳定。
- Query Key 包含所有影响查询结果的参数。
- 搜索输入有合理防抖。
- 删除成功后列表正确刷新。
- 加载、失败、空状态明确区分。
- 不在客户端缓存中存放密码等敏感数据。
- React Query Devtools 只在开发环境启用。

# 阶段七：搜索、标签与体验优化

## 33. 搜索策略

第一版可以使用 PostgreSQL 的基础模糊查询，搜索标题、摘要等明确字段。

需要确定：

- 搜索范围
- 是否区分大小写
- 空搜索词的行为
- 排序规则
- 分页参数

不要先返回所有文档再由前端过滤；数据量增加后，这种方式无法扩展，也可能泄露数据。

## 34. 标签策略

当前 `tags` 是 PostgreSQL 字符串数组，适合第一版。如果以后需要：

- 标签颜色
- 标签描述
- 标签合并
- 标签统计
- 标签权限

再考虑独立 `Tag` 模型和多对多关系。

不要为尚未出现的需求过早增加复杂数据模型。

## 35. 阶段验收标准

- 搜索和标签条件可以组合。
- 条件改变时缓存 Key 同步变化。
- 空搜索词有明确契约。
- 查询由数据库完成过滤和排序。
- 移动端和桌面端布局均可使用。

# 阶段八：个人设置与管理员用户管理

## 36. 个人设置

第一版建议支持：

- 昵称
- 邮箱
- 个人简介
- 修改密码

更新普通资料和修改密码应拆成两个操作。修改密码通常需要：

1. 验证当前密码。
2. 校验新密码规则。
3. 确认两次新密码一致。
4. 生成新的 bcrypt 哈希。
5. 根据安全策略决定是否让其他 Session 失效。

更新与 Session 相关的用户名、昵称或角色后，需要考虑 Session 是否刷新。这正是 SessionProvider 的一个实际用途。

## 37. 管理员用户管理

管理员模块建议支持：

- 查看用户列表
- 创建普通用户或管理员
- 修改用户角色
- 重置用户密码
- 禁用用户（需要后续增加状态字段）

所有管理操作必须在服务端检查：

```ts
session.user.role === "admin"
```

并考虑以下保护：

- 不允许管理员误删自己。
- 不允许系统失去最后一个管理员。
- 重置密码后不返回明文密码到日志。
- 用户名、邮箱唯一冲突返回明确业务错误。

## 38. 角色字段的后续升级

当前 `role` 是字符串，学习阶段可以继续使用。业务稳定后可以改为 Prisma Enum：

```prisma
enum UserRole {
  USER
  ADMIN
}
```

Enum 能减少 `admn`、`Admin` 等拼写错误，但修改时需要数据库迁移，应作为独立步骤完成。

## 39. 阶段验收标准

- 普通用户无法访问管理员页面。
- 普通用户直接调用管理 Action 也会被拒绝。
- 管理员能创建用户，密码以哈希保存。
- 个人资料更新后页面和 Session 显示一致。
- 修改密码必须验证当前密码。

# 阶段九：AI 助手

## 40. 为什么最后再做 AI

AI 功能依赖稳定的用户、文档和权限基础。如果知识库 CRUD 尚未完成，AI 很难安全地获取正确上下文。

## 41. 第一版范围

第一版只做：

- 输入问题
- 服务端调用模型
- 流式返回回答
- 显示用户消息和助手消息
- 允许中止生成
- 显示错误和重试

然后再逐步增加：

- 选择知识库文档作为上下文
- 文档摘要
- 引用来源
- 向量检索
- 对话历史持久化

## 42. 安全边界

- 模型 API Key 只能存在服务端。
- 服务端必须认证用户。
- 检索文档必须按当前用户 ID 过滤。
- 不能因为模型请求需要上下文，就读取其他用户文档。
- 流式接口需要处理断开和取消。

## 43. 阶段验收标准

- API Key 不进入客户端 Bundle。
- 未登录不能调用 AI 接口。
- 用户只能使用自己有权访问的文档作为上下文。
- 响应可以流式显示并中止。
- 请求失败时页面不会永久停留在加载状态。

## 45. Next.js 错误与加载状态

逐步补充：

```text
app/
├── loading.tsx
├── error.tsx
└── not-found.tsx
```

需要区分：

- 正在加载
- 数据为空
- 数据不存在
- 用户无权访问
- 可预期业务失败
- 不可预期系统异常

这些状态不能全部显示成“出错了”。

## 46. 环境变量与部署

部署前检查：

- `DATABASE_URL`
- `AUTH_SECRET`
- 正确的生产域名配置
- AI API Key（启用 AI 后）
- 不保留不再需要的 seed 明文密码
- 所有密钥都由部署平台管理

管理员初始化属于受控运维操作。正式环境初始化完成后，建议移除 `SEED_ADMIN_PASSWORD`，避免长期保存首次明文密码。

## 47. 字体与构建

当前项目使用 `next/font/google` 时，离线或受限网络环境可能导致生产构建无法下载字体。正式部署前建议：

- 使用项目内本地字体并通过 `next/font/local` 加载；或
- 使用稳定的系统字体栈。

不要让生产构建依赖不稳定的外部字体下载。

## 48. 最终验收标准

- `npx tsc --noEmit` 通过。
- `npm run lint` 通过。
- `npm run build` 通过。
- 登录、文档 CRUD、权限关键路径有 E2E 测试。
- 普通用户无法读取或修改他人资源。
- 管理员接口有服务端角色检查。
- 错误页面和加载状态完整。
- 环境变量没有提交到仓库。

# 50. 每一步的学习方式

后续每个功能都按照以下节奏推进：

1. 先说明该功能解决什么问题。
2. 画清楚请求、数据和权限流向。
3. 确定接口契约和组件职责。
4. 一次只实现一个最小闭环。
5. 运行类型检查、Lint 和必要测试。
6. 对照验收标准手动验证。
7. 最后复盘为什么这样设计，以及还有哪些替代方案。

遇到新技术时，优先回答三个问题：

1. 它解决的具体问题是什么？
2. 如果不用它，当前实现会遇到什么困难？
3. 它应该放在哪个最小作用域内？

只要这三个问题没有清晰答案，就暂时不要急着把新工具加入项目。
